runbook · on-call · incidents · drills

What to do when things break — and how to prevent that.

This is the on-call's pocket card. Every incident you're likely to face is here with a symptom, a verification step, and the smallest action that resolves it. Drills, escalation paths, and recovery procedures live at the bottom.

1 · On-call

One primary, one secondary, in 7-day rotations. Handoff Mondays at 10:00 IST.

Primary

First responder. Acknowledges within 5 min.

  • Carries the pager (PagerDuty)
  • Owns mitigation, not root cause
  • Posts updates every 15 min until resolved
  • Cuts the incident channel

Secondary

Backup if primary doesn't ack in 5 min.

  • Pulled in for S1 incidents
  • Helps with comms and timeline
  • Runs the postmortem the next week

Escalation

When you need help.

  • Engineering lead — S1 unresolved 30 min
  • CTO — patient safety risk identified
  • Hospital ops lead — patient-facing outage > 15 min
  • DPO — any PII exposure suspected

The on-call kit

  • Laptop with wrangler logged into the prod account.
  • Phone with PagerDuty + 2FA app.
  • Bookmarks: Sentry · CF Analytics · CF Workers logs · D1 console · status page.
  • VPN credentials for admin console access.
  • This runbook printed and pinned somewhere physical.

3 · The first 5 minutes

When the pager goes off, do these in order. Don't skip steps.

  1. Ack the page in PagerDuty.
  2. Open a Slack thread in #ops-incidents. Pin the alert. Name it INC-YYYY-MM-DD-<short>.
  3. Confirm the symptom yourself: hit /health, open the affected SPA, look at Sentry.
  4. Classify severity using the table above. Update the channel.
  5. Stop the bleeding before investigating. Common mitigations:
    • Rollback the last deploy — wrangler rollback --env production
    • Flip a feature flag in KV — see feature flags
    • Disable a noisy notification channel via the admin console
    • Add a CF rule to rate-limit an abusive IP
  6. Update the channel every 15 min, even with "still investigating".
Stop the bleeding before you investigate. Restoring service is more important than knowing why it broke. Root cause is for the postmortem.

4 · Incident runbooks

Symptom → verify → mitigate → confirm.

IR-1 · Authentication is down S1

Symptom: users can't log in; spike of 5xx on /v1/auth/login.
Verify
curl https://api.…/v1/auth/login -d '…' returns 5xx · Sentry has new auth-service errors
Common causes
Last deploy broke a route · D1 binding mis-set · JWT_SECRET rotated only in one service · KV exhausted limit
Mitigate
(1) wrangler rollback --env production on auth-service. (2) If KV: temporarily extend rate-limit TTL via dashboard. (3) If JWT mismatch: re-deploy gateway + auth together with same secret.
Confirm
Synthetic /me probe goes green · login succeeds from incognito · Sentry error rate drops to baseline within 5 min

IR-2 · Critical notifications not delivering S1

Symptom: ops dashboard escalation queue grows · MSG91 or push delivery rate < 90%.
Verify
Ops dashboard → escalations export · notifications.sent_to_json[].status = failed
Common causes
Provider outage · Credentials expired · Rate-limited at provider · Bad phone numbers in seed/import
Mitigate
(1) Admin console → flip primary channel to backup (SMS → Telegram, etc.). (2) Replay failed deliveries from the escalation export. (3) If MSG91 throttling: stagger sends over 2 min.
Confirm
Delivery rate > 95% on the next 100 messages · No new entries in escalation queue for 10 min

IR-3 · ABDM / ABHA upstream errors S2

Symptom: abdm_upstream errors on enrol / link · ABDM status page shows red.
Verify
curl …/api/v1/platform/abha/operational-readiness · ABDM public status page
Mitigate
Set FF_ABHA_ENROLL = false in KV — UI shows "ABHA temporarily unavailable, you can still register without it." Patient flow keeps working.
Confirm
Signup completes via Profile ID fallback · No ABHA calls fail in the last 5 min after flag flip

IR-4 · Database hot path S2

Symptom: D1 query p95 > 1 s · API write latency tripled.
Verify
CF Analytics D1 panel · trace a single slow request in Sentry to find the query
Common causes
Missing index on a new query · A long-running migration · Big JSON column read on hot endpoint
Mitigate
(1) Add the missing index via wrangler d1 execute (additive, safe). (2) Cache the offending read in KV for 30 s. (3) Restrict to projected columns, defer JSON read.
Confirm
p95 returns to < 250 ms · D1 panel shows query gone from top-N

IR-5 · Lab webhook backlog S2

Symptom: lab.resulted events not arriving for > 30 min · external lab dashboard shows queued.
Verify
Sentry filter service:lab-service · Ops dashboard "lab last seen" tile
Mitigate
If our endpoint is up: ask lab to replay. If our verification rejected (HMAC mismatch): rotate the shared secret in admin console, ask lab to replay.
Confirm
Latest order moves from in-lab → resulted · Patient + clinician notified

IR-6 · Telegram bot stops responding S3

Symptom: bot stops echoing /start; webhook 4xx in CF logs.
Verify
curl https://api.telegram.org/bot<TOKEN>/getWebhookInfo — look at last_error_message
Mitigate
(1) Re-set webhook with correct secret. (2) Confirm TELEGRAM_WEBHOOK_SECRET matches in Workers Secrets. (3) Use ops dashboard "drill checklist" to ping all bot routes.

IR-7 · PII exposure suspected S1

Symptom: log line shows Aadhaar or full DOB · audit shows out-of-tenant read.
Verify
Grep the last 24h of logs for the offending field · re-run the audit query that flagged it
Mitigate
(1) Stop new writes — flip FF_READ_ONLY = true. (2) Page the DPO. (3) Begin breach assessment per DPDP playbook. (4) Don't delete logs — preserve evidence.
Confirm
Source plugged · Affected users counted · DPIA breach template started · 72-hour clock noted
DPDP Act 2023: data breach must be reported to the Data Protection Board within 72 hours.

IR-8 · Cloudflare regional outage S1

Symptom: edge unreachable from some geos · CF status page yellow/red.
Verify
cloudflarestatus.com · independent test from downforeveryoneorjustme.com
Mitigate
Communicate to hospital ops — front-desk should switch to offline intake forms (paper). Update status page. Wait it out; nothing useful we can do at edge layer.

5 · Deploy procedure

Two humans on the call. Pre + post checklists.

Pre-deploy

  1. Staging green for ≥ 24 h.
  2. Migration plan reviewed by 2 engineers.
  3. Manual snapshot labelled pre-deploy-….
  4. Slack post in #ops with SHA + approver.
  5. Sentry + CF Analytics open in tabs.

Deploy

  1. GitHub Actions → deploy-production → ref main.
  2. Watch the job: snapshot → migrate → services → pages → probe.
  3. If probe fails, abort and rollback (next section).

Post-deploy

  1. Synthetic probes green for 5 min.
  2. No new Sentry fingerprints in first 10 min.
  3. p95 latency within +20% of previous baseline.
  4. Confirm in #ops: "Deployed #<sha> ✓".
  5. Watch the system for 30 min before logging off.

Deploy windows

  • Tue / Wed / Thu, 10:00–15:00 IST.
  • No Friday afternoon deploys.
  • No deploys during a critical event (hospital launch day, big patient drive).
  • Off-hours emergency deploys require CTO approval in writing.

6 · Rollback

Fast. Atomic. Tested every quarter.

Worker rollback (services)

# revert to previous deployed version of a single service
cd services/<svc>
wrangler deployments list --env production
wrangler rollback --env production --message "INC-2026-05-21"

Takes < 60 s. Affects only that service. Repeat per service if multiple were deployed.

Pages rollback (apps)

# Cloudflare Pages dashboard → choose previous deployment → "Rollback"

Atomic — old version is restored at all edges in under a minute.

Migration rollback

Migrations are additive only: new tables, new columns, new indices. Drop columns are scheduled in a separate "removal" PR ≥ 1 sprint later, after all callers stop using them.

If a migration causes incident: revert the Worker (so old code stops writing the new column), leave the column in place, schedule a fix.

7 · Backup

Schedule

  • Auto: daily 03:00 IST → R2 pulseward-backups/auto/YYYY-MM-DD.json
  • Retention: last 7 hot, then weekly to cold tier for 1 year, then archive.
  • Manual: curl -X POST https://api.…/v1/backup/snapshot with admin token
  • Pre-deploy: CI takes a snapshot before any prod migration
  • All snapshots are AES-256 encrypted at rest with a per-tenant envelope key

Verify a snapshot exists today

wrangler r2 object list pulseward-backups --prefix auto/

# expect: auto/<today>.json with size > 1 MB and recent uploaded timestamp

8 · Restore

Test it. Quarterly drill is non-negotiable.

Full restore procedure

  1. Decide the snapshot: wrangler r2 object list pulseward-backups --prefix auto/
  2. Download it: wrangler r2 object get pulseward-backups/auto/2026-05-19.json > snap.json
  3. Restore to sandbox first: 
    node scripts/restore.js \
  --input snap.json \
  --target sandbox \
  --tenant main \
  --confirm
  4. Smoke test the sandbox tenant — log in, fetch a few records, run a booking.
  5. Announce maintenance: flip FF_MAINTENANCE = true on production.
  6. Apply restore to production: node scripts/restore.js --target production --tenant main --confirm
  7. Smoke test production: same as step 4.
  8. Flip back: FF_MAINTENANCE = false.
  9. Audit-log the action automatically captured; verify it appears.
RTO target: < 1 hour from "decide" to "users back in". RPO < 24 hours (worst case lose a day).

11 · Drills

Restore drill — quarterly

  1. Pick a random 7-day-old auto-backup.
  2. Restore to a fresh sandbox tenant.
  3. Time the operation from kickoff to "users could log in".
  4. Run a fixed smoke-test script against the restored data.
  5. Compare row counts to source-of-truth from that day.
  6. Document the time + any surprises in the runbook diff.

Failover drill — quarterly

  1. Pick one service. Simulate failure with FF_<svc>_DEGRADED.
  2. Confirm the system continues with degraded mode (e.g. notifications drop to fewer channels).
  3. Time recovery once flag flips back.
  4. Update the IR runbook if behavior was unexpected.

Security drill — annual

  1. OWASP ZAP scan against staging.
  2. Pen-test by a third party.
  3. Tabletop exercise: pretend a clinician account is compromised.
  4. Verify DPIA + breach playbook are current.

Load drill — pre-launch + bi-annual

  1. k6: 100 concurrent users for 30 minutes against staging.
  2. k6: spike to 500 for 60 s; expect graceful 503s on overflow.
  3. Confirm no DB corruption; alert thresholds fired correctly.

12 · Postmortem template

For any S1 / S2 incident. Blameless. Within 5 business days.

# INC-2026-MM-DD — <short title>

Severity: S1 / S2
Duration: HH:MM IST → HH:MM IST (Xm)
Detected by: alert | user report | manual
Owner: @<name>
Author: @<name>

## Impact
- Users affected: N
- Records mis-served: N
- SLO budget consumed: X%

## Timeline (IST, 24h)
- 09:12 — first alert fires
- 09:14 — primary acks
- 09:18 — rolled back to #abc123
- 09:22 — confirmed mitigation
- 09:45 — incident closed

## What went wrong
<technical narrative>

## What went right
<detection, comms, mitigation>

## Root cause
<the actual underlying mechanism — code, config, ops>

## Action items
- [ ] (owner, due) Add alert on metric X
- [ ] (owner, due) Add test for case Y
- [ ] (owner, due) Update runbook IR-N
- [ ] (owner, due) Migration approved by 2 engineers gate
Blameless rule: postmortems describe systems, not people. "The deploy process let a missing migration ship" — not "X forgot to run the migration". The fix lives in the system.
