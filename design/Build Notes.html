1 · Final repo layout

Single monorepo. One source tree, three deployable targets (patient/clinician web, admin, mobile). The existing apps/ + services/ structure from the GitHub repo maps directly.
pulseward-hms/ ├─ apps/ # client deploy targets │ ├─ portal/ # patient + clinician (single SPA) │ │ ├─ index.html │ │ ├─ src/ # React app — exact prototype code │ │ └─ vite.config.js │ ├─ admin/ # admin console (separate deploy) │ │ ├─ index.html │ │ └─ src/ # mounts admin routes only │ └─ mobile/ # Capacitor shell │ ├─ capacitor.config.json │ ├─ android/ # native projects │ └─ ios/ ├─ services/ # backend (one Worker per service) │ ├─ api-gateway/ # Hono router + auth middleware │ ├─ auth-service/ │ ├─ patient-service/ │ ├─ appointment-service/ │ ├─ ehr-service/ │ ├─ lab-service/ │ ├─ pharmacy-service/ │ ├─ billing-service/ │ ├─ notification-service/ # telegram, push, email, SMS fan-out │ ├─ abha-service/ # ABDM proxy │ └─ backup-service/ # cron-triggered snapshot Worker ├─ packages/ # shared code │ ├─ schema/ # Zod schemas + types — used by app AND services │ ├─ ui/ # shared React components │ └─ sdk/ # typed client (replaces IndexedDB layer) ├─ migrations/ # drizzle SQL migrations ├─ docs/ # runbooks, ABHA spec, API catalog └─ .github/workflows/ # CI/CD
From prototype → repo: the existing src/*.jsx files map to apps/portal/src/ (rename Babel-loaded scripts into ES modules; Vite picks them up unchanged). The src/db.jsx IndexedDB layer gets replaced by packages/sdk with the same function signatures — so React components don't change.

Implement auth endpoints
argon2id hash (server-side) + JWT access token (15m) + opaque refresh token in KV (30d).
// services/api-gateway/src/routes/auth.ts
import { Hono } from 'hono';
import { zValidator } from '@hono/zod-validator';
import { hash, verify } from '@node-rs/argon2';
import { signJwt } from './jwt';
import { z } from 'zod';

const SignupSchema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
  password: z.string().min(8),
  dob: z.string().optional(),
  gender: z.enum(['M', 'F', 'O']),
  phone: z.string().regex(/^\+?[0-9 ]{10,15}$/),
});

const app = new Hono();

app.post('/signup', zValidator('json', SignupSchema), async (c) => {
  const body = c.req.valid('json');
  const db = c.env.DB;

  // rate limit by IP
  await rateLimit(c.env.RATELIMIT, c.req.header('cf-connecting-ip') ?? '?', 5, 3600);

  const existing = await db.prepare('SELECT id FROM users WHERE email = ?').bind(body.email).first();
  if (existing) return c.json({ ok: false, error: 'email_taken' }, 409);

  const ph = await hash(body.password + c.env.PEPPER);

  const patientId = crypto.randomUUID();
  const userId = crypto.randomUUID();
  const tenantId = 'main';  // or look up from origin header for multi-tenant

  await db.batch([
    db.prepare('INSERT INTO patients (id, tenant_id, mrn, profile_id, name, dob, gender, phone, email, created_at) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?)')
      .bind(patientId, tenantId, mrn(tenantId), 'PID-' + uid(5), body.name, body.dob, body.gender, body.phone, body.email, Date.now()),
    db.prepare('INSERT INTO users (id, tenant_id, email, password_hash, role, linked_entity_id, created_at) VALUES (?, ?, ?, ?, ?, ?, ?)')
      .bind(userId, tenantId, body.email, ph, 'patient', patientId, Date.now()),
  ]);

  const token = await signJwt({ uid: userId, role: 'patient', tid: tenantId }, c.env.JWT_SECRET, 15 * 60);
  const refresh = crypto.randomUUID();
  await c.env.SESSIONS.put(`rt:${refresh}`, userId, { expirationTtl: 30 * 86400 });

  audit(c, { actor: body.email, action: 'patient_signup', scope: `pat:${patientId}` });
  setCookie(c, 'rt', refresh, { httpOnly: true, secure: true, sameSite: 'Strict', maxAge: 30 * 86400 });
  return c.json({ ok: true, token, role: 'patient' });
});

Build typed SDK
Replace IndexedDB layer in the React app with HTTP calls. Same function names — UI unchanged.
// packages/sdk/client.ts
export class PulseWardClient {
  constructor(private base: string, private getToken: () => string | null) {}
  private async req(path: string, init?: RequestInit) {
    const r = await fetch(`${this.base}${path}`, {
      ...init,
      headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${this.getToken() ?? ''}`, ...init?.headers },
      credentials: 'include',
    });
    if (!r.ok) throw new Error(await r.text());
    return r.json();
  }
  signup(b) { return this.req('/v1/auth/signup', { method: 'POST', body: JSON.stringify(b) }); }
  login(b)  { return this.req('/v1/auth/login',  { method: 'POST', body: JSON.stringify(b) }); }
  patients = { list: () => this.req('/v1/patients'), get: (id) => this.req(`/v1/patients/${id}`) };
  appointments = { ... };
  // 1:1 with the IndexedDB store API surface
}

5 · Week 3 — ABHA + Telegram bot

3 Integrations

The two integrations that make this a real Indian healthcare product.

ABHA / ABDM

  • HFR onboarding complete; client_id + secret saved.
  • Implement abha-service Worker as a thin proxy to ABDM v3 endpoints.
  • Aadhaar OTP: POST /v1/abha/request-otp → /verify-otp → /suggestions → /set-address.
  • Cache ABDM access tokens in KV (10-min TTL — re-fetch on miss).
  • RSA-encrypt Aadhaar with ABDM public cert before sending.
  • Store ABHA number + address on patient row; emit audit + welcome notification.
  • Implement HIP callback at /v1/abdm/callback for consent and data-fetch requests.

Telegram bot

  • Set webhook: https://api.../v1/telegram/webhook?secret=...
  • Verify X-Telegram-Bot-Api-Secret-Token on each request.
  • Commands: /start · /link <code> · /book · /labs · /rx · /cancel.
  • Link patient identity: patient generates a 6-digit code in the portal; sends /link 123456 on Telegram; bot resolves to user_id and stores chat_id.
  • For reminders: notification-service fetches chat_id and calls sendMessage with inline keyboard buttons.
// services/abha-service/src/routes/enrol.ts
app.post('/v1/abha/request-otp', async (c) => {
  const { aadhaar } = await c.req.json();

  const abdmToken = await getCachedToken(c.env);
  const encrypted = await rsaEncrypt(aadhaar, c.env.ABDM_PUBLIC_CERT);

  const r = await fetch(`${ABDM_BASE}/v3/enrollment/request/otp`, {
    method: 'POST',
    headers: {
      Authorization: `Bearer ${abdmToken}`,
      'Content-Type': 'application/json',
      'REQUEST-ID': crypto.randomUUID(),
      'TIMESTAMP': new Date().toISOString(),
    },
    body: JSON.stringify({
      txnId: '',
      scope: ['abha-enrol'],
      loginHint: 'aadhaar',
      loginId: encrypted,
      otpSystem: 'aadhaar',
    }),
  });

  return c.json(await r.json());
});

7 · Admin console separation

Same React codebase, different deployment. The point is a defence-in-depth boundary, not a separate engineering effort.

What stays shared

  • All components in packages/ui
  • Design tokens, icons, fonts
  • SDK / API client
  • Auth, session handling

What differs in admin

  • Entry HTML mounts only admin routes (no patient/clinician views).
  • Hosted at admin.your-hospital.in (separate Pages project).
  • WAF: IP allow-list (hospital office IPs + VPN range).
  • 2FA required (TOTP minimum, WebAuthn for super-admin).
  • Backend rejects admin endpoints from any other origin via signed origin header.
  • JWT scope check: role === 'admin' || 'ops' before any handler runs.
  • No public sign-up. Admins are seeded or invited by existing admins.

export default {
  async scheduled(event, env) {
    const snap = {};
    for (const table of TABLES) {
      const rows = await env.DB.prepare(`SELECT * FROM ${table}`).all();
      snap[table] = rows.results;
    }
    const ts = new Date().toISOString().slice(0, 10);
    const body = JSON.stringify(snap);
    await env.BACKUPS.put(`auto/${ts}.json`, body, {
      customMetadata: { tenant: 'main', kind: 'auto', version: '1' },
    });

    // Rolling retention: keep last 7 auto + roll older to cold tier
    const list = await env.BACKUPS.list({ prefix: 'auto/' });
    const sorted = list.objects.sort((a, b) => b.uploaded.getTime() - a.uploaded.getTime());
    for (const obj of sorted.slice(7)) {
      // Move to weekly cold tier (rename key prefix)
      // or env.BACKUPS_COLD.put(...)
    }
  },
};

Restore procedure

  1. Identify snapshot: wrangler r2 object list pulseward-backups --prefix auto/
  2. Download: wrangler r2 object get pulseward-backups/auto/2026-05-19.json > snap.json
  3. Apply to a sandbox D1: node scripts/restore.js sandbox snap.json
  4. Smoke test the sandbox tenant.
  5. Maintenance window: swap DNS or apply restore to prod D1.
  6. Audit log entry written automatically.

11.6 · Observability

If you can't see it, you can't run it. Four pillars: logs, metrics, traces, audits — each with a default tool and what it costs.

Structured logs

  • Every request emits one JSON line: trace_id · route · status · ms · user · tenant.
  • Workers Logs (CF dashboard) for live tailing. wrangler tail --env production.
  • Sentry for unhandled errors + sourcemaps. Free tier covers 5k events / month.
  • No PII in logs — middleware redacts password, aadhaar, otp, refresh_token by key.

Metrics

  • Cloudflare Analytics: traffic, edge latency, 4xx/5xx by route.
  • Workers Analytics Engine for custom counters: notify.delivered, appt.book.conflict, abha.enrol.success.
  • D1 panel: top slow queries, storage growth, rows scanned.
  • Operations dashboard reads notif + ABHA telemetry endpoints (see ops README).

Traces

  • Every request gets a trace_id in X-Trace-Id; propagated to internal service calls.
  • Sentry stitches spans across services automatically when SDK is initialized in each Worker.
  • Search a trace by ID across the whole stack in 1 click.

Audit

  • Append-only audit_events on every write.
  • Daily roll-up Worker exports to R2 cold tier for cheap multi-year retention.
  • Admin console has a search-by-actor view; ops uses it for compliance dumps.
  • Read access is logged too (just at lower frequency to avoid noise).

11.7 · Testing strategy

Production-ready means we know the system works under load and after every change. Coverage matters less than confidence at each layer.

Unit (Vitest)

  • Pure logic in packages/* + services/*/lib
  • FSM transition tables (every legal/illegal combination)
  • Validators, MRN generator, drug interaction lookups
  • Coverage gate: 80% on schema + FSM modules
  • Run on every PR

Integration (miniflare)

  • Spin Workers + local D1 file in-process
  • One file per route folder
  • Snapshot the JSON response shape — drift fails CI
  • Includes the auth middleware + audit middleware

Contract

  • packages/schema/openapi.ts emits OpenAPI 3
  • pnpm run contracts:check compares prod schema to repo
  • SDK clients regenerated automatically from the schema
  • Breaking changes require a major bump + migration plan

End-to-end (Playwright)

  • Booking flow · lab review flow · ABHA link flow
  • Runs against an ephemeral preview env per PR
  • Visual regression on Storybook stories
  • Smoke suite runs against staging post-deploy

Load (k6)

  • 100 concurrent users, 30 min sustained
  • Targets: p95 < 250 ms, error < 0.1%
  • Spike: 500 concurrent for 60 s → must not 503 the gateway
  • Run before launch & bi-annually

Security

  • OWASP ZAP baseline nightly on staging
  • pnpm audit + Dependabot on every PR
  • CodeQL on push to main
  • Third-party pen-test before public launch
Definition of "production ready": all six test layers green on staging for 14 consecutive days plus one successful restore drill. Then we roll one department.

13 · Go-live checklist

Run through this T-7 days before launch.

T-7 days

  • Full restore drill on sandbox tenant from latest backup. RTO clocked < 1h.
  • Load test: 100 concurrent users for 30 minutes; p95 < 250ms.
  • OWASP ZAP scan against staging; resolve all High/Critical.
  • Dependency audit — pnpm audit shows no High/Critical.
  • All Workers Secrets rotated; staging secrets ≠ prod secrets.
  • DPIA document signed off; DPO designated.
  • Incident response runbook printed and pinned in the ops channel.
  • On-call schedule for week 1 published (one engineer for 2-hour windows, rotating).

T-1 day

  • Take a manual snapshot before any deploy.
  • Migrate prod schema; run smoke test against prod URL.
  • Verify Telegram webhook is set and responding.
  • Verify ABHA sandbox calls succeed end-to-end.
  • Set up status page (CF Workers + a simple template).
  • Pre-create the first 5 clinician accounts; share temp passwords offline.
  • Bookmark Sentry dashboard, Cloudflare Analytics, and the audit log.

Launch day

  • Soft launch in one department (Cardiology). Don't open the portal URL publicly yet.
  • Front-desk staff trained — they're your tier-1 support.
  • Hourly Sentry check for the first 8 hours.
  • EOD: take a manual snapshot labelled "Launch day".
  • Stand-down: write a launch-day retro the next morning.

Days 1–14 (soft launch window)

  • Daily standup with the cardiology team — capture every friction.
  • One ticket = one PR. No batched changes.
  • Watch p95 latency, error rate, and patient sign-up funnel.
  • If anything looks off, you have rollback and restore one click away.
  • Day 14 review: if metrics are clean, expand to the next 2 departments.

14 · After go-live

  • Month 2: roll the rest of the hospital. Optional WhatsApp connector. Insurance API for cashless flow.
  • Month 3: productionize ABHA (move from sandbox to production endpoints). HIP callback completeness review.
  • Month 6: second hospital onboarded. Multi-tenant code paths get real exercise.
  • Quarterly: DR drill, secret rotation, dependency audit, DPIA refresh, on-call rotation review.
