Stateless, edge-deployed

System layers

How a single request (e.g. POST /v1/appointments) flows through.

Client
Patient web · Clinician web · Admin web · Mobile (Capacitor) · Telegram chat — all use the same JSON API.
Edge
Cloudflare Pages serves static React. Workers handle api.your-hospital.in/v1/*, including bot webhooks & ABDM callbacks. WAF + rate-limiting on the edge.
API Gateway
Hono router → Auth middleware (JWT validate) → Tenant middleware (resolve hospital from JWT claim) → Audit logger → Route handler.
Services
Modular service files: auth, patient, appointment, ehr, lab, pharmacy, billing, notification. Same shape as the existing services/* folders in the repo.
Data
D1 (relational) · R2 (blobs) · KV (cache & sessions). All tagged with tenant_id; every query filters by it.
External
ABDM Sandbox / Prod · Telegram Bot API · FCM & APNs · SMTP (Resend / SES) · Insurance APIs (later).

Email + password is enough for v1. ABHA-OAuth is a v1.1 follow-up (the patient can sign in with their ABHA address instead).

Current prototype: uses SHA-256 + salt in the browser (via SubtleCrypto) since it has no backend. In production, hashing happens server-side with argon2id. The client never holds the salt.

ABHA / ABDM integration

Aligned with ABDM v3 endpoints. The hospital onboards once (Health Facility Registry); patients then create or link an ABHA from inside the portal.

Hospital onboarding (one-time)

  • Apply at facility.abdm.gov.in → receive HFR ID.
  • Register an ABDM client at facility.abdm.gov.in/sandbox → get client_id / client_secret.
  • Store secrets in CF Secrets; cache short-lived access tokens in KV.
  • Stand up the Health Information Provider (HIP) callback at /v1/abdm/callback.

Patient ABHA creation

1
Request OTP
Patient enters Aadhaar (12 digits) or mobile (10 digits) in the portal.
POST /v3/enrollment/request/otp
2
Verify OTP & enrol
ABDM returns ABHA number + tokens.
POST /v3/enrollment/enrol/byAadhaar
3
Pick address
Show 4–5 suggestions; let patient pick name@abdm.
GET /v3/enrollment/enrol/suggestion
POST /v3/enrollment/enrol/abha-address
4
Persist
Save abha_number + abha_address on the patient row. Emit audit + welcome notification.

Fallback: Profile ID

For patients who can't / won't link ABHA right away.

A profile_id (PID-XXXXX) is auto-generated at signup and works inside the hospital. It cannot share records outside the facility — that's the only feature gap vs. ABHA. The portal nags gently to link ABHA but never blocks care.

// Worker route — request ABHA OTP
import { Hono } from 'hono';
const app = new Hono();

app.post('/v1/abha/request-otp', async (c) => {
  const { aadhaar } = await c.req.json();
  const abdmToken = await getAbdmToken(c.env);   // KV-cached
  const encrypted = await rsaEncrypt(aadhaar, ABDM_PUBLIC_CERT);
  const r = await fetch(`${c.env.ABDM_BASE}/v3/enrollment/request/otp`, {
    method: 'POST',
    headers: { Authorization: `Bearer ${abdmToken}`, 'Content-Type': 'application/json',
               REQUEST-ID: crypto.randomUUID(), TIMESTAMP: new Date().toISOString() },
    body: JSON.stringify({ txnId: '', scope: ['abha-enrol'], loginHint: 'aadhaar',
                           loginId: encrypted, otpSystem: 'aadhaar' }),
  });
  return c.json(await r.json());
});

One codebase for everything

Lowest operational cost = fewer codebases to maintain. PulseWard is built so the same React build covers web, mobile, and (with one shim) the admin console.

Patient + Clinician web

React + Vite, served as static from Cloudflare Pages
  • Same JSX trees, same components, same data layer.
  • Role is loaded from the JWT on sign-in and routes are guarded.
  • Installable as a PWA — works offline once seeded.

Mobile (iOS & Android)

Capacitor — same web build wrapped natively
  • No React Native fork; npx cap add ios android on the existing repo.
  • Native plugins for push (FCM/APNs), camera (photo upload), biometric unlock.
  • Submit to App Store / Play Store from the same git tag that ships web.

Admin console

Optionally a separate origin for security
  • Same React codebase, different entry HTML — admin.html mounts only the admin routes.
  • Deployed to a different sub-domain (admin.your-hospital.in) with stricter WAF rules: IP allow-list, hardware key 2FA, no public sign-up.
  • Front-end auth blocks any session whose role ≠ admin/ops.
  • Backend rejects admin endpoints from anywhere except the admin origin via CORS + signed origin headers.
Why split admin? Defence-in-depth. Even if a patient/clinician session token leaks, it can't reach admin endpoints — they require both a different JWT scope AND a different origin. The cost is one extra static deploy, not a separate codebase.

Backups & disaster recovery

In production, the prototype's IndexedDB layer is replaced by D1 / Postgres — the snapshot routine is the same shape, just running server-side on cron.

Automatic (rolling 7 days)

Every 24h
  • Cloudflare Cron Trigger fires the backup Worker at 03:00 IST.
  • Dumps each table to a .jsonl.zst stream into R2.
  • Rolling retention: most recent 7 daily snapshots kept hot, older ones moved to R2 cold tier.
  • Encrypted at-rest (R2 default) + AES-256 per-tenant key.
// wrangler.toml
[triggers]
crons = ["0 21 * * *"]   # 03:00 IST

Manual (kept forever)

On-demand from Admin Console
  • Admin → Backups → "Manual snapshot" creates a labelled forever-kept backup.
  • Use before release, schema migration, or bulk delete.
  • Downloadable as a single JSON file for off-platform archive.

Restore

Two paths
  • One-click in Admin Console — overwrites everything atomically.
  • Off-platform JSON — upload via the Admin restore-from-file picker.
  • Quarterly DR drills: practice restore on a sandbox tenant, score RTO < 1h, RPO < 24h.

Clinician tasks — Eisenhower matrix

Tasks auto-sort into four quadrants for natural prioritization.

Do first

Urgent · Important

Drop everything and finish. Examples: sign off on critical labs, return urgent patient call.

Schedule

Important · Not urgent

Block calendar time. Examples: CME, case conference prep, journal reading.

Delegate

Urgent · Not important

Hand to nursing / admin if possible. Examples: insurance forms, routine refills.

Eliminate or later

Not urgent · Not important

Trim. Examples: low-priority surveys, optional reading.

From prototype → production

Every screen in the current prototype is wireable to a real endpoint. This is the order I'd build them in.

Week 1 — backend skeleton

  • Provision Cloudflare account + D1 + R2 + KV.
  • Bring up Hono on Workers with /health.
  • Apply schema migrations (drizzle-kit).
  • Auth: /v1/auth/signup, /login, /refresh.
  • Patient CRUD: /v1/patients.

Week 2 — clinical workflows

  • Appointments & scheduling.
  • Notes, prescriptions, lab orders.
  • Notifications service: in-app + email.
  • Replace IndexedDB store in the React app with real fetch calls (one tiny client per resource).

Week 3 — ABHA + bot

  • HFR onboarding completed.
  • ABHA enrolment endpoints proxied.
  • Telegram bot webhook live; link-by-phone command.

Week 4 — mobile + go-live

  • Capacitor wrap; FCM/APNs push wired.
  • Restore drill, load test, security review.
  • Soft launch with a single department for 2 weeks before rolling hospital-wide.
