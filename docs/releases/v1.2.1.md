# PulseWard Release 1.2.1 (In Progress)

Status: Draft snapshot for active milestone delivery

## Summary

This snapshot captures the post-1.2.0 hardening work delivered across M1 contract reliability, M2 auth/admin configurability seed, M3 core clinical workflow hardening (through M3.6 billing trigger hooks), M4 scheduling and notification reliability hardening (through M4.4 dead-letter and telemetry), M5 connector diagnostics and runbook hardening (through M5.4), and M6 admin console operational scaffold.

  - Semantic route/spec contract parity checks.
  - Drift reconciliation across gateway, EHR, lab, and billing services.
  - Strict parity mode enabled in CI.
  - Regression tests added to prevent drift reintroduction.
  - Critical endpoint request/response schema coverage checks added for auth, booking, and notification APIs.

  - Replaced pnpm cache/install execution in CI/CD/security workflows with npm lockfile-aligned execution.

## Migration Notes

1. Pull the latest `.env.example` values into deployment secret stores.
2. Validate contracts and route loading:
   - `npm run contracts:check -- --strict`
   - `npm run test:routes`
3. Validate integration config and smoke behavior:
   - `npm run integrations:validate`
   - `npm run test:smoke`
4. For ABHA checks, ensure `ABHA_GATEWAY_BASE_URL`, `ABHA_CLIENT_ID`, and `ABHA_CLIENT_SECRET` are set with real values.
5. For M4.2/M4.4 event wiring and reliability checks, configure `APPOINTMENT_NOTIFICATION_EVENT_ENDPOINT` (and optionally `APPOINTMENT_NOTIFICATION_MAX_RETRIES`, `APPOINTMENT_NOTIFICATION_TIMEOUT_MS`, `APPOINTMENT_NOTIFICATION_LATE_THRESHOLD_MS`, `APPOINTMENT_NOTIFICATION_DEAD_LETTER_MAX`) where appointment-service must fan out lifecycle events and classify reminder reliability outcomes.
6. For M5.1 WhatsApp diagnostics readiness, configure `INTEGRATION_WHATSAPP_CREDENTIALS` with `accessToken` and either `phoneNumberId` or `senderNumber` where WhatsApp Cloud API is enabled.
7. For M5.2 website webhook diagnostics, optionally configure `INTEGRATION_WEBHOOK_ENDPOINT` override and `INTEGRATION_WEBHOOK_SIGNING_SECRET` for signing readiness checks.
8. For M5.2 ABHA operations readiness, ensure runbook procedures in `docs/runbooks/abha-operational-readiness.md` are part of weekly integration validation.
9. For M5.3 webhook signature verification, submit canonical payload plus `signature` to `POST /api/v1/integrations/messaging/webhook/signature/verify` using `sha256=<hex-hmac>` format.
10. For M5.3 ABHA incident drill automation, archive `GET /api/v1/platform/abha/health-check/evidence` output alongside readiness snapshots.
11. For M5.4 retry controls, configure optional env keys (`INTEGRATION_RETRY_POLICY`, `INTEGRATION_RETRY_MAX_ATTEMPTS`, `INTEGRATION_RETRY_BASE_DELAY_MS`, `INTEGRATION_RETRY_MAX_DELAY_MS`, `INTEGRATION_RETRY_JITTER`) and validate through `GET /api/v1/integrations/messaging/retry-policy`.
12. For M5.4 ABHA operational drills, execute `GET /api/v1/platform/abha/consent-flow/simulation?scenario={happy-path|consent-denied|gateway-timeout}` and archive output with readiness evidence.
