Part 1.5 · Clone & install dependencies

1

Clone the monorepo

All apps, services, packages live here.
git clone [email protected]:your-org/pulseward-hms.git
cd pulseward-hms
2

Install workspace dependencies

pnpm hoists shared deps so a single install covers all apps + services.
pnpm install
Don't run npm install — it ignores the workspace topology and will leave broken symlinks. If you see "module not found" errors after install, you almost certainly have a stale node_modules; nuke it with pnpm -r exec rm -rf node_modules and re-run.
3

Bootstrap secrets & local .env

Copies .env.example templates into place. None of these are real credentials — they just unblock dev.
pnpm run setup:env

If the script doesn't exist yet (greenfield setup), copy by hand:

# For each app + service that ships a .env.example:
find . -name '.env.example' -not -path '*/node_modules/*' -exec sh -c 'cp "$1" "${1%.example}"' _ {} \;

Part 2 · Run it all locally

Three terminals minimum. Five is more comfortable.

1

Initialize the local database

Drizzle migrations against a local SQLite file. Seed adds 50 demo patients + 3 clinicians.
pnpm run db:migrate          # applies migrations/*.sql to .data/local.db
pnpm run db:seed             # tenants, users, patients, appointments, notifications

Inspect with: sqlite3 .data/local.db ".tables".

2

Start the backend services (terminal #1)

A single command spawns all seven services on their assigned ports. Watch mode reloads on file change.
pnpm run dev:services

Or start individually:

pnpm run start:auth          # :5101
pnpm run start:notification  # :5102 + :8088
pnpm run start:appointment   # :5103
pnpm --filter ehr-service dev
pnpm --filter lab-service dev
pnpm --filter pharmacy-service dev
pnpm --filter abha-service dev
3

Start each web app (terminal #2 onward)

Vite dev servers proxy /api/v1 → local services. Each gets its own port so you can run them side by side.
# Patient portal
pnpm run install:patient
pnpm run start:patient:dev     # http://localhost:4313

# Clinician portal
pnpm run start:clinician:dev   # http://localhost:4311

# Admin console
pnpm run start:admin:dev       # http://localhost:4180

# Operations dashboard
pnpm run start:operations:dev  # http://localhost:4312

# Landing page (static, no API needed)
pnpm run start:landing         # http://localhost:4173
4

One-shot: bring everything up

turbo handles dependency order across services + apps.
pnpm run dev                 # turbo run dev — services first, then apps
Tip: open http://localhost:4173 first — the landing console links to every other surface and tells you which services it can or can't reach.

First-run smoke test

~5 minutes. If anything below fails, jump to Troubleshooting before going further.

  1. API reachable: curl http://127.0.0.1:8087/health → { "ok": true, "ver": "1.0.0" }
  2. Auth signup works: open localhost:4313 → "Create account" → expect to land in patient dashboard.
  3. Appointment booking: book any clinician for tomorrow 10:00 → returns 201 → shows on dashboard.
  4. Clinician sees it: log in as [email protected] (seed) on localhost:4311 → appointment shows on tomorrow's day view.
  5. Notification fan-out: in the operations dashboard, the notification telemetry trend should tick by 1.
  6. Admin reachability check: localhost:4180 → all three services show healthy.
  7. Local restore drill: pnpm run backup:snapshot --local → file lands in .data/backups/; pnpm run db:restore .data/backups/<file>.json sandbox succeeds.
Done? You have a working dev stack. Commit your .env templates with placeholders (never values) and open a PR.

Mobile app

Expo managed workflow. Android first; iOS optional once you have a $99 Apple Developer account.

  1. Install Expo Go from Play Store on your phone.
  2. Make sure phone + laptop are on the same Wi-Fi.
  3. Find your laptop's LAN IP (ipconfig getifaddr en0 on macOS).
  4. Set env in PowerShell or bash: 
    EXPO_PUBLIC_PULSEWARD_HOST=192.168.1.50
EXPO_PUBLIC_PULSEWARD_API_BASE_URL=http://192.168.1.50:5102
EXPO_PUBLIC_PULSEWARD_AUTH_BASE_URL=http://192.168.1.50:5101
pnpm run start:mobile:lan
  5. Scan the QR code in the terminal with the camera app (iOS) or Expo Go (Android).
  6. Tap Enable push and get token → Send test push.
  7. Notification arrives within seconds.
Don't use 127.0.0.1. Your phone can't reach your laptop's loopback. Always use the LAN IP.

Part 4 · Deploy to staging

One push to main triggers staging deploy. Confirm via the URL printed in CI.

1

Provision Cloudflare resources (one-time per environment)

wrangler d1 create pulseward-staging
wrangler kv namespace create SESSIONS_STAGING
wrangler kv namespace create RATELIMIT_STAGING
wrangler r2 bucket create pulseward-staging-uploads
wrangler r2 bucket create pulseward-staging-backups

Note each ID; paste into services/*/wrangler.toml under [env.staging].

2

Push secrets

cd services/api-gateway
wrangler secret put JWT_SECRET --env staging
wrangler secret put PEPPER --env staging
wrangler secret put ABDM_CLIENT_ID --env staging
wrangler secret put ABDM_CLIENT_SECRET --env staging
wrangler secret put ABDM_PUBLIC_CERT --env staging
wrangler secret put TELEGRAM_BOT_TOKEN --env staging
wrangler secret put RESEND_API_KEY --env staging
wrangler secret put MSG91_AUTH_KEY --env staging
wrangler secret put SENTRY_DSN --env staging
3

Run migrations

wrangler d1 migrations apply pulseward-staging --remote --env staging
4

Push main — CI does the rest

git push origin main
# GitHub Actions: pnpm test → build:apps → wrangler deploy --env staging

Each service is its own Worker; CI deploys them in parallel. Pages are atomic per build.

5

Smoke test staging

curl https://staging-api.your-hospital.in/health
# {"ok":true,"ver":"1.0.x","env":"staging"}

# Run the end-to-end Playwright suite against staging
pnpm run e2e -- --env=staging

Production deploy

Manual trigger; protected by a production-approver GitHub team. Two humans on the call, always.

Pre-deploy (5 min)

  1. Confirm staging green for ≥ 24 hours.
  2. Manual snapshot via backup-service webhook trigger — labelled pre-deploy-YYYY-MM-DD.
  3. Open the prod Cloudflare Analytics dashboard in another tab.
  4. Post in #ops: "Deploying #<sha> to prod, approver: @<name>".

Deploy

# In GitHub Actions UI
Run workflow → deploy-production
Inputs:
  ref: main
  approver: <your GH handle>
  migrate: true      # run migrations before app deploy

The job: (1) takes a snapshot, (2) runs migrations, (3) deploys services in parallel, (4) deploys pages atomically, (5) runs the post-deploy probe.

Post-deploy (15 min)

  1. Probe: curl https://api.your-hospital.in/health returns the new SHA.
  2. Hit five hot endpoints from a real browser session.
  3. Watch Sentry for new error fingerprints — none should appear in the first 10 min.
  4. Watch p95 latency — no > 20% regression vs. previous deploy.
  5. If anything looks off: wrangler rollback --env production — back online in < 60 s.
  6. Update #ops: "Deployed #<sha> ✓".
Never deploy on a Friday afternoon. Deploy windows: Tue/Wed/Thu 10:00–15:00 IST. Any other slot needs an explicit override in the PR description.

Daily workflow

Morning

  • git pull --rebase
  • pnpm install if lockfile changed
  • pnpm run dev brings everything up
  • Skim Sentry digest, check overnight alerts

Per change

  • Branch off main with a ticket prefix
  • Co-locate schema → service → SDK → UI changes in one PR
  • pnpm test before pushing
  • PR requires 1 review + CI green

Weekly

  • Dependabot PR review (Monday)
  • One restore drill on staging
  • Read Sentry weekly report
  • Walk the audit log for any unusual actor activity

Quarterly

  • Rotate all Workers Secrets
  • Refresh ABDM sandbox creds
  • Run DPIA refresh checklist
  • On-call rotation review
